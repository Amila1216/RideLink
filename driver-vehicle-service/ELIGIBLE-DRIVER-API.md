# Eligible Driver Search (Section 3B)

## Interservice contract

Ride Management calls `GET /api/v1/drivers/eligible` over HTTP. It sends the required `serviceArea` query parameter and may set `requireLocation=true` when its search requires a driver to have a simulated current location. The service area is trimmed and compared without case sensitivity against the Section 2 `drivers.service_area` value. There is no service-area catalogue in this service, so any nonblank value up to 100 characters is accepted as a search value.

The optional location flag only requires both existing simulated coordinates to be present and within the Section 2 latitude/longitude bounds. It does not compare distance or perform route matching. Ride Management does not send coordinates or location data in this request.

Successful responses contain a `drivers` array. Each result contains the stable `driverId`, `availability`, and each complete vehicle's `vehicleId` and `vehicleType`. Contact details, license information, service-area details, and coordinates are not returned. No matches return HTTP `200` with an empty `drivers` array.

Ride Management must use this service API and must never connect to or query the Driver & Vehicle Service database directly. The Driver & Vehicle Service currently has no configured authentication or role-based authorization mechanism. Calls are unauthenticated in this application; an environment gateway may enforce identity and return `401` or `403`, but those responses are not generated by this service today. Do not send credentials unless the deployment provides an agreed gateway contract.

## OpenAPI

The endpoint is documented in the Driver & Vehicle Service Swagger UI at `/swagger-ui.html` and OpenAPI JSON at `/v3/api-docs`.

| Result | HTTP status | Body |
| --- | --- | --- |
| Search completed, with or without matches | `200` | `EligibleDriverSearchResponse`; no matches use `{"drivers":[]}` |
| Missing, blank, or overlong `serviceArea` | `400` | Existing `ApiError` shape |
| Authentication rejected by a deployment gateway | `401` | Gateway-defined |
| Role/permission rejected by a deployment gateway | `403` | Gateway-defined |
| Unexpected service/data failure | `500` | Existing `ApiError` shape |

Example request:

```http
GET http://localhost:8083/api/v1/drivers/eligible?serviceArea=Colombo&requireLocation=true
```

There is no request body. `serviceArea` is required; `requireLocation` is optional and defaults to `false`.

The query options represented as JSON for a Ride Management client are:

```json
{
  "serviceArea": "Colombo",
  "requireLocation": true
}
```

This object is translated into URL query parameters; it is not sent as a GET body.

Successful response:

```json
{
  "drivers": [
    {
      "driverId": 12,
      "availability": "AVAILABLE",
      "vehicles": [
        {
          "vehicleId": 34,
          "vehicleType": "SEDAN"
        }
      ]
    }
  ]
}
```

No-driver response:

```json
{
  "drivers": []
}
```

Validation error follows the existing `ApiError` structure:

```json
{
  "timestamp": "2026-10-01T12:00:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "{serviceArea=Service area is required}",
  "path": "/api/v1/drivers/eligible"
}
```

## Postman integration flow

Set `baseUrl` to `http://localhost:8083` and use Postman's response IDs in subsequent path values.

1. Create a profile with `POST {{baseUrl}}/api/v1/drivers`, JSON body:

   ```json
   {
     "firstName": "Alex",
     "lastName": "Rider",
     "email": "alex.rider@example.com",
     "phoneNumber": "+1234567890",
     "licenseNumber": "DL-POSTMAN-1",
     "driverAvailability": "AVAILABLE"
   }
   ```

2. Add a vehicle with `POST {{baseUrl}}/api/v1/drivers/{{driverId}}/vehicles`, JSON body:

   ```json
   {
     "make": "Toyota",
     "model": "Corolla",
     "year": 2022,
     "licensePlate": "POST-001",
     "color": "Silver",
     "vehicleType": "SEDAN",
     "registrationNumber": "POST-REG-1"
   }
   ```

3. Set the Section 2 area with `PUT {{baseUrl}}/api/v1/drivers/{{driverId}}/service-area`, JSON body `{"serviceArea":"Colombo","serviceAreaDetails":"Central"}`.
4. Set the Section 2 simulated location with `PUT {{baseUrl}}/api/v1/drivers/{{driverId}}/location`, JSON body `{"latitude":6.9271,"longitude":79.8612}`.
5. Set Section 3A availability with `PUT {{baseUrl}}/api/v1/drivers/{{driverId}}/availability`, JSON body `{"status":"AVAILABLE"}`.
6. Search with `GET {{baseUrl}}/api/v1/drivers/eligible?serviceArea=Colombo&requireLocation=true`. Confirm the response contains `driverId` and the created `vehicleId`.
7. Negative availability case: set status to `UNAVAILABLE` using the same Section 3A request, repeat the GET, and confirm the driver's ID is absent (and the array is empty if no other driver qualifies).
8. Negative area case: create and configure another driver with service area `Kandy`, set it to `AVAILABLE`, then search for `Colombo`. Confirm that driver's ID is absent.

## Build and test

From the `driver-vehicle-service` directory:

```sh
mvn package
mvn test
mvn spring-boot:run
```

The application listens on port `8083` by default.
